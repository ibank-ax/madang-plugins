# 개발 가이드 · dev18.v1
> guideVersion: 2.12.0 · sourceDigest: 5f71c53620a8eff20fa738706a4e335590f3d0a3d109d9f0a5ff3ec0a77862a3

- 프로젝트의 실제 workflowVersion·runId를 조회해요. dev12.v1의 구 번호와 dev18.v1의 안정 단계 키를 섞지 않고, 새 18단계 실행은 버전을 지원하는 서버의 run API로 진행해요.
- 기존 단계 ID·번호·보고·결정·첨부·배포 기록을 보존하고 완료 상태를 새 번호로 복제하지 않아요.
- 운영 중인 서비스 개선은 기존 등록·유효한 결정·근거를 재사용해요. 초기 등록·전체 18단계 재시작·최초 오픈을 다시 요구하지 않아요. 17단계는 검증된 개선 반영, 18단계는 운영 지속 확인으로 읽어요.
- 가이드 공급·설치·OAuth 연결·실제 IDE 과업은 별도 근거예요. 보호 SSH/Git·중단/재개·13역할 결과 취합은 실제 실행 근거 없이 통과로 표시하지 않아요.
- 위키 활성/과거/목표/결정 필요를 구별해요. 실행 근거는 versionId/nodeKey/contentHash/docVersion/sourceDigest/retrievedAt로 고정하고 활성 버전이 바뀌어도 과거 근거를 덮어쓰지 않아요. 이 가이드는 새 위키 표준의 활성 승인이 아니에요.

## 1. 인터뷰·자료 수집 (requirements)
- 입력: 사용자 요청과 기존 자료
- 행동: 최초 사용자 요청·추가 정정·기존 docs·현행 코드/API·허용된 원격 read-only를 수집하고 출처/시각/버전을 기록한다. 실제 요구·전문가 제안·사용자만 결정할 항목을 구별한다.
- 결과물: 출처·확정/목표/미확인과 요구 ID
- 완료 기준: 프로젝트의 전체 세부 요구 ID, 현행/목표/불일치/미확인, 재사용/보완/새 작성 판단, 비밀 입력/조회 경로 목록이 있다. 자료에 없는 인터뷰 답을 생성하지 않는다.
- 담당: 기획 · 리서치
- 근거: 기획 주도, 리서치·PM 검토. 요구 원문 참조와 소스 commit·원격 조회 revision이 근거이며 현행 자료 조회는 신규 기능 통과가 아니다.
- 경계: 자료에 없는 인터뷰 답변을 만들지 않아요.
- 다음: basic_planning

## 2. 기본 기획 (basic_planning)
- 입력: 출처가 연결된 요구
- 행동: 단계01 요구로 사람/직접 에이전트/플러그인의 사용자 과업, 정상·실패·취소·재개, 정책·권한·결정 재사용·용어를 정한다.
- 결과물: 사용자 과업·정책·수용 기준
- 완료 기준: 프로젝트 전체 요구의 수용 기준·범위·성공/실패 판단·자연스러운 한국어 문구가 있고 승인 답변과 실제 완료를 구별한다.
- 담당: 기획 · PM
- 근거: 기획 주도, PM·일반인/전문가 고객 역할 검토. 문서 버전·요구 대응이 근거이며 실제 사람 이해도는 단계16에서 측정한다.
- 경계: 결정 답변과 실제 작업 완료를 구분해요.
- 다음: basic_design

## 3. 기본 설계 (basic_design)
- 입력: 과업과 수용 기준
- 행동: A 보호 입력→중앙 비밀→전용 실행→ID/상태, B 같은 issueId의 결정/작업/증거, C 버전/기록 전환을 먼저 결정한다. 자동 준비 6범주·일시 중단·재개·원격 환경·추가 비용 경계를 연결한다.
- 결과물: 신뢰 경계·권한·복구·자동 준비 설계
- 완료 기준: 신뢰 경계·우회 차단·권한·상태/예외·환경/외부 자원 대조·복구 설계가 있다. requireUser/마스킹/금칙 명령만으로 격리를 주장하지 않는다.
- 담당: 백엔드 · 인프라 · 보안 · DBA
- 근거: 백엔드·인프라·보안·DBA 공동, PM 검토. 구조도/위협 경계/불변식·비용 미확인 목록이 산출이며 실행 증거는 단계12 이후다.
- 경계: 마스킹이나 금지 명령만으로 비밀 격리를 주장하지 않아요.
- 다음: information_architecture

## 4. IA (information_architecture)
- 입력: 과업과 기존 URL
- 행동: 현행 메뉴·권한·모드·전체 기능을 대시보드/프로젝트/이슈/개발 위키 네 기본 메뉴에 배치한다. 전역/프로젝트 범위와 관리자 보조 진입을 보존한다.
- 결과물: 네 메뉴·이동·구 URL 대응
- 완료 기준: 기존 기능마다 정확한 도착 위치가 있고 사라진 메뉴가 기능 삭제로 이어지지 않는다. 보고서·개발/운영 작업·결정·연결 설정의 진입이 명확하다.
- 담당: 기획 · 디자이너
- 근거: 기획·디자인, 프론트 검토. 현행 메뉴→신규 화면 ID 대응이 근거다.
- 경계: 개발·운영·결정은 같은 이슈 화면의 보기예요.
- 다음: page_map

## 5. 페이지 맵 (page_map)
- 입력: IA와 기존 페이지
- 행동: 전체 경로/query/hash/프로젝트 선택·역할·모바일/알림/첨부 링크를 목록화하고 구 URL 어댑터를 정한다.
- 결과물: URL·보기·시스템 상태·비웹 표면 목록
- 완료 기준: 페이지 분모와 기존→신규 URL, 진입/다음/뒤로가기·권한 없음·없는 기록·전환 중 도착 규칙을 모두 연결한다.
- 담당: 기획 · 프론트
- 근거: 프론트·기획, 보안/DBA 검토. 경로 목록·redirect/resolve 계약이 근거이며 실제 이동은 단계15에서 확인한다.
- 경계: 페이지·카드·익스텐션을 하나의 분모로 합치지 않아요.
- 다음: page_specification

## 6. 모든 페이지 상세 기능 (page_specification)
- 입력: 전체 페이지 맵
- 행동: 페이지마다 버튼/폼/메뉴/조회·생성·수정·삭제·실행을 실제 API 입력/응답/오류/권한에 대응한다. 로딩/빈 상태/취소/충돌/만료/키보드/360~375px를 명시한다.
- 결과물: 행동·API·권한·오류·취소·재개 계약
- 완료 기준: 전체 페이지×필수 상태의 작성/미적용 사유/누락 분모가 있고 보호 입력을 에이전트가 대신 채우는 동작이 없다.
- 담당: 기획 · 프론트 · 백엔드
- 근거: 기획·프론트, 백엔드/디자인 검토. 기능 명세·API DTO·권한 행위 목록이 근거다.
- 경계: 저장 성공을 실제 실행 성공으로 표시하지 않아요.
- 다음: schema

## 7. 스키마 (schema)
- 입력: 상세 기능과 데이터 계약
- 행동: 동일 프로젝트 관계와 ID 보존, issue-decision-task-evidence, 버전/run, 영구 operation/step/retry/resource reconciliation을 가산적으로 설계한다.
- 결과물: ID·상태·제약·이전·복구 계획

- 담당: DBA · 백엔드
- 근거: DBA·백엔드, 보안/인프라 검토. 스키마/이전 manifest/대조 쿼리 설계가 근거다. 로컬 DB 적용은 하지 않는다.
- 경계: 기존 번호·관계·보고를 보존하며 로컬 DB를 쓰지 않아요.
- 다음: wireframes

## 8. 목업·와이어프레임 (wireframes)
- 입력: 페이지별 상세 계약

- 결과물: 전체 화면·하위 표면·주요 상태 목업
- 완료 기준: 전체 화면 분모와 목업 대응이 있고 mock·설계 산출임을 표시한다. 상호작용을 설명한 그림을 실제 구현/연결 증거로 쓰지 않는다.
- 담당: 디자이너 · 프론트
- 근거: 디자인·프론트, 일반인/전문가 고객 역할 검토. 목업 파일·화면/상태 대응이 근거다. 로컬 브라우저/서버는 사용하지 않는다.
- 경계: 정적 목업을 실제 제품 검수 통과로 세지 않아요.
- 다음: design_system_draft

## 9. 디자인시스템 초안 (design_system_draft)
- 입력: 목업과 기존 토큰
- 행동: 현행 토큰·컴포넌트를 조사해 색/타이포/간격/크기/포커스/문구/상태를 재사용한다. 임의의 새 최상위 메뉴나 장식으로 요구를 늘리지 않는다.
- 결과물: 타입·색·여백·컴포넌트 기준
- 완료 기준: 기본 토큰과 컴포넌트 목록, 재사용/보완/신규 사유가 있으며 비밀 원문 표출 컴포넌트는 목표 목록에서 제외한다.
- 담당: 디자이너
- 근거: 디자인 주도, 프론트/접근성 검토. 토큰 출처·컴포넌트 계약이 근거다.
- 경계: 기존 디자인 토큰과 제품 문구를 먼저 재사용해요.
- 다음: design_system_complete

## 10. 전체 컴포넌트·레이아웃 보강 (design_system_complete)
- 입력: 전체 표면과 DS 초안
- 행동: 모든 페이지/주요 상태를 공통/개별 컴포넌트·레이아웃에 대응하고 긴 한국어·오류·키보드·모바일 규칙을 마감한다.
- 결과물: 전체 대응·모바일·키보드·긴 내용 기준
- 완료 기준: 전체 페이지·상태·기능·데이터·목업·DS 연결에서 누락이 0이고 의도적인 미적용에는 사유가 있다. 다음 단계 파일 담당과 수용 조건이 지정된다.
- 담당: 디자이너 · 프론트
- 근거: 디자인·프론트, 기획/PM 검토. 1~10 설계 패키지와 작성 분모가 근거다. 구현/배포 통과는 아직 0이다.
- 경계: 하위 UI와 오류·권한·만료 상태도 포함해요.
- 다음: frontend_publishing

## 11. 프론트 퍼블리싱 (frontend_publishing)
- 입력: 설계·목업·DS
- 행동: 1~10 패키지를 받아 전체 페이지·상태·상호작용을 구현한다. 화면별 mock 표시를 유지하고 실제 API 완료로 표기하지 않는다. 변경 후 commit→push→원격 검수 배포한다.
- 결과물: mock 화면과 원격 퍼블리싱 증거
- 완료 기준: 모든 화면/필수 상태가 원격에서 열리고 360/375/데스크톱·키보드·긴 문구·deep link를 확인한다. A/B/C가 필요한 버튼은 안전한 mock/비활성 사유를 표시한다.
- 담당: 프론트 · 디자이너
- 근거: 프론트 주도, 디자인·기획 검토. 배포 web revision·화면/상태 케이스·이미지가 근거다.
- 경계: 실제 연결과 미연결 API를 표시하고 외부 발송을 하지 않아요.
- 다음: backend_implementation

## 12. 백엔드 (backend_implementation)
- 입력: A/B/C 계약과 데이터 설계
- 행동: 승인된 설계의 도메인 서비스/DB/REST/MCP/worker를 구현한다. 보호 입력/전용 실행/구 reveal 차단, 동일 이슈 계약, 버전·원자성·영구 operation을 먼저 완성한다.
- 결과물: 공통 서비스·REST/MCP·worker·스키마
- 완료 기준: API/worker revision이 맞고 권한·입출력 허용 목록·교차 프로젝트 거부·경쟁/재시도·구 소비자 차단이 원격 검수에서 통과한다. 서버 health만으로 완료하지 않는다.
- 담당: 백엔드 · DBA · 보안
- 근거: 백엔드·DBA·보안·인프라. 원격 서비스/DB/worker별 revision·계약 시험·정제된 감사가 근거다.
- 경계: 일반 에이전트에 자격 원문이나 임의 실행 권한을 주지 않아요.
- 다음: live_integration

## 13. 실제 연결 (live_integration)
- 입력: 퍼블리싱과 실제 API
- 행동: 퍼블리싱 mock을 실제 서비스와 연결하고 생성→저장→재조회→권한별 확인→실행/증거까지 같은 issueId로 확인한다. 자동 준비 6범주와 실제 SSH/Git 브리지의 허용된 경로를 각각 시험한다.
- 결과물: HTTP 연결·DTO 대조·mock 잔존 목록
- 완료 기준: 페이지×기능의 실연결 분모에 mock/폴백 미완료가 남지 않고 외부 성공 후 저장 실패·unknown 대조·철회/만료·구 URL/플러그인 혼합이 처리된다.
- 담당: 프론트 · 백엔드
- 근거: 프론트·백엔드 공동, 인프라·보안 검토. API와 인증 UI·외부 자원 ID의 연결 증거가 필요하며 등록 성공만으로 실제 사용을 인정하지 않는다.
- 경계: mock 화면 통과와 실 API 연결 완료를 분리해요.
- 다음: synthetic_validation

## 14. 실제 구조의 합성 데이터 연결 검수 (synthetic_validation)
- 입력: 제공 환경 안의 격리된 검수 프로젝트와 합성 데이터셋
- 행동: 격리된 원격 검수 프로젝트에 실제 스키마를 쓰는 비밀 없는 합성 데이터를 준비한다. 기존12/신18, 역할별 사용, 결정 재사용, 재시도/복구·이전 대조를 시험한다.
- 결과물: CRUD·권한·오류·동시성·정리 증거
- 완료 기준: 프로젝트에 확정한 합성 데이터 검수 케이스와 전체 요구/페이지/상태 회귀의 분모·통과·실패·미확인을 고정한다. 고객 데이터 복제나 mock-only 통과를 합성 데이터 검수로 집계하지 않는다.
- 담당: DBA · 백엔드 · 보안
- 근거: 백엔드·프론트·DBA, PM/보안 검토. seed manifest·revision·caseId·정리 결과가 근거다.
- 경계: 운영 자료와 섞지 않고 unknown 외부 자원을 자동 삭제하지 않아요.
- 다음: ai_e2e

## 15. AI E2E (ai_e2e)
- 입력: 같은 환경·배포 버전의 실제 연결
- 행동: 배포된 HTTPS에서 실제 UI를 탐색·클릭·입력해 네 메뉴·역할·오류·모바일·구 링크·세 IDE 작업을 수행한다. 보호 폼은 에이전트가 입력하지 않고 사람 입력 완료 상태의 안전한 시험 자격으로 경로를 검수한다.
- 결과물: 요청→결정→작업→배포→결과의 브라우저 증거
- 완료 기준: 프로젝트의 AI E2E 케이스·IDE별 6항목·전체 브라우저 회귀가 명확한 분모로 통과한다. API-only·정적 렌더·AI의 추정 완료는 UI 증거가 아니다.
- 담당: 프론트 · 보안 · 리서치
- 근거: 프론트/백엔드·고객 역할 에이전트, 보안 독립 검토. 원격 URL·시각·web/API-worker revision·실제 클릭/기대/실제·정제 이미지가 근거다.
- 경계: API 호출만으로 실제 브라우저 과업을 대신하지 않아요.
- 다음: human_validation

## 16. 실제 사람 시험 (human_validation)
- 입력: 실제 사용 시나리오와 참여자
- 행동: 구체적 시험 계획·검수 환경·시간·과업·동의된 참여자를 준비하고 실제 사람이 직접 수행한다. AI가 결과를 대신 답하지 않는다.
- 결과물: 사람의 수행·이해·접근성 결과와 피드백
- 완료 기준: 프로젝트의 실제 사람 시험 케이스를 실제 사람이 판단하고 발견 이슈·재시험·제한을 같은 issueId/회차에 연결한다. 필요 참여가 없으면 미확인으로 남기며 단계15로 대체하지 않는다.
- 담당: 실제 사람 · 기획
- 근거: 실제 사용자/검수자, 기획·PM 진행, 개발 지원. 수행 주체·날짜·과업 결과·관찰·수정/재시험이 근거다. 실제 사람 참여는 별도 일정 경계다.
- 경계: AI 역할 검토를 실제 사람의 결과로 기록하지 않아요.
- 다음: production_release

## 17. 최종 운영 배포 (production_release)
- 입력: 허용된 대상·검증된 revision·복구점
- 행동: 검수 통과 commit·설정/스키마 호환·구 소비자·마이그레이션 계획·구체적 rollback/복구점·허용 범위를 묶는다. 이미 유효한 대상·환경·작업 범위에서 해당 프로젝트에 등록된 app→web 배포 설정의 순서를 따르며 미승인 범위·새 비용·파괴적 영향이 있을 때만 해당 차이를 결정으로 연결한다.
- 결과물: app→web 배포와 인증된 운영 경로·복구 근거
- 완료 기준: 프로젝트의 운영 반영 케이스, 운영 API/worker/web revision·인증 경로·차단 조건·기록 대조가 통과한다. PR 머지·health·검수 배포를 운영 배포 완료로 간주하지 않는다.
- 담당: 인프라 · PM
- 근거: 인프라·백엔드·프론트, 보안/PM 검토. 유효한 허용 범위와 배포/롤백 이력·운영 측정 근거로 완료를 판단하며 새 사람 승인 단계를 추가하지 않는다. 단계16 실제 사람 시험의 근거는 별도로 유지한다.
- 경계: 유효한 허용 범위 안에서 실행해요. 새 비용·파괴적 영향 등 실제 범위 차이만 결정으로 다뤄요.
- 다음: service_transition

## 18. 실서비스 시작·운영 전환 (service_transition)
- 입력: 운영 배포와 책임·모니터링·백업 기준
- 행동: 이미 유효한 대상·환경·허용 작업 범위에서 실서비스를 시작하고 운영 담당·연락/알림·장애 대응·백업·복구·구 URL/플러그인 전환·남은 위험·비용/AI 한도·검수 자원 정리를 연결한다. 비밀은 인계문서 대신 보호 저장소 참조 ID/상태로만 연결한다.
- 결과물: 운영 담당·잔여·복구·인계와 전환 근거
- 완료 기준: 단계17 실제 운영 배포와 프로젝트의 운영 지속 검수·전체 요구 근거가 있고 미해결 차단이 0이며 조건부 항목은 담당·기한·판정이 있다. 운영모드 값/인계 파일 존재만으로 완료하지 않는다. 근거가 갖춰지면 서비스가 완료를 기록하며 단계18만을 위한 새 사람 승인 절차를 두지 않는다.
- 담당: PM · 인프라 · 운영 담당
- 근거: 운영 담당·PM, 인프라·보안·예산 역할. 감시/알림 수신·백업/복구 결과·자원 정리·인계 수령과 잔여 항목이 근거다. 실제 미승인 범위·새 비용·파괴적 영향이 발견되면 그 차이에만 결정을 연결하고, 단계16 실제 사람 시험은 그대로 별도 근거로 유지한다.
- 경계: 단계 자체에 추가 승인 버튼을 만들지 않아요. 실행·운영 증거를 대조해요.
- 다음: 운영 지속 근거와 잔여 담당 확인

현재 IDE 단계 명령: /dev-go. 실제 단계 전이는 조회한 실행의 workflowVersion·runId·stageKey 계약을 따라요.

## 프로젝트 지식과 결정 추천
- 개발 위키는 공통·프로젝트가 선택한 개발 지침이고 프로젝트 위키는 그 프로젝트의 이슈 맥락·해결 방법·주의사항·재사용 결정과 기억이에요. 둘을 검색 출처와 용도에서 구별하고 다른 프로젝트 지식을 섞지 않아요.
- 개발·수정·검수·운영에서 재사용할 지식은 허용된 프로젝트에서 create_project_wiki/update_project_wiki로 출처·관련 이슈와 함께 지속 등록·갱신해요. project 위키는 get_project_wiki_document/search_project_wiki로 현재 버전·내용 해시와 실제 본문 근거를 읽고 참조해요. 기존 감사·접속정보 원문을 통째로 복제하거나 임베딩하지 않아요. 비밀값은 입력하지 않아요.
- 프로젝트 위키 문서 저장과 실제 색인 준비는 별개예요. indexState/indexedVersion/현재 모델·차원과 semantic/lexical 모드를 확인하고 실패는 같은 문서의 reindex_project_wiki로 보완해요. 키워드 fallback을 실제 의미 검색으로 보고하지 않아요. 개발 위키의 표준 활성 승인과 프로젝트 지식의 권한 내 자율 등록은 서로 다른 절차예요.
- 마당 계열의 개발 위키·프로젝트 위키 임베딩은 google/gemini-embedding-2와 명시 dimensions=1536으로 통일하는 것이 확정 전환 기준이에요. 입력 문서·질의 요청·저장·검색에 같은 모델과 차원을 사용해요. 기준 확정·가이드 공급·실제 활성 전환은 구별하고, 현재 활성 모델과 검수 당시 모델은 실제 근거대로 기록해요.
- 기존 원문·기존 모델 색인을 보존한 채 새 모델의 별도 색인을 만들어요. 모델·차원·원문 해시·색인 버전별로 저장 영역과 질의/색인 캐시를 분리하고, 같은 1536차원이어도 다른 모델의 벡터를 섞지 않아요. 기존 원문 해시의 완료 색인은 중복 생성하지 않고 실패는 같은 작업·저장 영역에서 중복 실행 방지를 적용해 재개하며 기존 작업 handle을 회수해요.
- 새 모델의 실제 반환 모델·1536 응답과 고정한 대상 범위의 색인 완료를 확인해요. 같은 모델·차원의 원격 의미 검색과 권한·삭제·갱신 검색을 검수한 뒤 활성 전환해요. 기존 검수 중 모델에 의존하는 부분만 새 근거로 보완하고 유효한 비모델 근거·과거 모델 검수 이력은 보존해요. 기존 색인을 먼저 지우거나 어휘 검색 결과로 의미 검색 완료를 대신하지 않아요.
- 실제 선택지가 있는 새 결정은 create_issue_decision에 selectionMode와 recommendation을 함께 넣어요. 단일 선택은 실제 optionKeys 한 개, 복수는 실제 조합, 승인·반려는 실제 행동과 짧은 reason을 적어요. 목록·상세·변경안 카드의 같은 decision/version/대상 추천을 확인하고 사용자 최종 선택과 따로 기록해요.
- 미결 결정의 추천이 빠졌거나 대상·선택지·버전이 달라졌으면 get_issue_work로 현재 맥락을 읽고 recommend_issue_decision으로 같은 결정에 보완해요. 과거에 없던 추천을 만들어 완료 이력에 넣거나 추천으로 답·승인·작업 완료를 대신하지 않아요. 정보 질문에 실제로 없는 선택지나 행동을 만들지 않아요.

## PM과 전문가 추론 설정
- 사용자가 고른 모델을 유지해요. PM은 생성·재개 때 현재 엔진·클라이언트·실제 모델이 지원하고 정책상 허용하는 최고 추론 강도를 조회해 실제 설정하고 적용값을 확인해요. 이름이 같은 강도를 서로 다른 클라이언트의 같은 값으로 추정하지 않아요.
- 전문가는 PM이 과업의 복잡도·위험·속도를 보고 지원 범위 안에서 강도와 짧은 이유를 정해 실제 배정에 적용해요. 작업관리자는 모든 작업에 필수로 관여하고 나머지 전문가는 필요한 역할만 실제 슬롯 안에서 배정해요. 예산관리자는 주간 한도 소진 위험이나 초기 인프라 발주안 검토에 관여해요. 기존 서브에이전트를 재사용하며 고정 12개 독립 대화나 전문가 일괄 최고 강도로 바꾸지 않아요.
- 지원 근거(엔진·클라이언트 버전·실제 모델·지원 목록·상한·조회 시각), 선택 강도와 이유, 설정 경로와 도구 수락값, 실제 실행의 관측값·확인 상태를 나누어 기존 배정·진행 보고·인계에 남겨요. 부모의 설정이나 도구의 배정 수락만으로 자식 실행에 적용됐다고 표시하지 않아요.
- 프롬프트의 ‘최고 강도로 생각’은 실제 설정 근거가 아니에요. 직접 설정·관측이 불가능하면 그 사실과 해당 클라이언트의 설정·확인 경로를 남겨요. 설정을 위해 재로그인·승인 요청을 반복하거나 진행 중인 대화를 불필요하게 새로 만들지 않아요.
- 재개·모델 fallback·정책 상한 변경 뒤에는 실제 모델과 적용 강도를 다시 대조해요. 직접 API를 쓰면 주 모델·fallback의 설정과 실제 요청 본문을 각각 확인하고 서버·worker·SDK가 명시한 강도를 조용히 바꾼 상태를 성공으로 기록하지 않아요. 설정 관측만으로 역할 과업 완료를 대신하지 않아요.

### Cursor
- Cursor CLI 공개 매개변수에는 범용 --effort가 없어요. 설치된 CLI의 --help·--list-models가 실제 제공하는 모델/variant를 확인하고, 기존 모델을 유지하는 지원 variant가 있을 때만 --model로 선택해요. 지원 variant나 적용 관측이 없으면 미확인과 실제 설정 경로를 남겨요. 근거: https://cursor.com/docs/cli/reference/parameters
- Cursor의 MAX 모드는 문맥·요금 모드이므로 최고 추론 강도 적용 근거로 세지 않아요. IDE는 해당 버전의 설정 기능을 확인하고 실제 선택·실행 관측을 분리해요. 사용자가 IDE 실검수·로그인·대기를 제외했다면 그 범위를 다시 시작하지 않아요. 근거: https://cursor.com/docs/models-and-pricing#max-mode

## 협업과 인계
PM은 기존 별도 대화에서 목표·분모·의존성을 조율해요. 작업관리자는 모든 작업에 필수로 관여하고 기존 서브에이전트를 재사용하며 없을 때만 실제 슬롯 안에서 배정해요. 나머지 전문가는 필요에 따라 배정하고 명령마다 새 세션·호출을 만들지 않아요. 시작 목표·완료 조건·재사용 근거·다음 결과와 예상 점검 시점을 확인하고 묶음 종료나 정체 징후 때 진행·중복·방법을 점검해요. 완료 조건 충족·유효 산출·장애 해결 없이 같은 실패·진단·계획·시험이 반복되면 원인을 짚고 중단·근거 재사용·방법 변경·필요한 병렬화 또는 근거가 갖춰진 즉시 완료 판정을 제안해요. 살아 있는 원격 작업의 정상 대기와 구별하며 timeout만으로 재실행하지 않아요. 재시험은 관련 변경·원인 수정·새 위험·미해결 근거의 구체적 이유가 있을 때 영향 범위만 확인해요. 예산관리자는 기존 점검 흐름에서 같은 계정·같은 주간 한도창의 usedPercent·remainingPercent·resetAt과 시간차 관측을 재사용해 72시간 내 소진이 전망될 때만 관여해 과다 토큰·긴 컨텍스트·중복 역할·시험을 줄이는 PM 권고를 내요. 표본·계측이 부족하면 전망·비용을 미확인으로 남기고 정상시 상시 에이전트를 호출하지 않아요. 프로젝트 초기 인프라 발주안에는 토큰 위험과 별개로 관여해 실제 수요·가용성·월비용 대비 CPU·RAM·스토리지·서버 수와 초기 규모·확장 조건을 검토해요. 필요한 보안·백업·가용성을 삭제하거나 최저 사양을 강제하거나 새 구매를 실행하지 않아요. 두 역할은 기존 서브에이전트·점검 시점·조사 근거를 재사용하고 진행·방법과 사용량·성과 대비 낭비를 나눠 맡아요. 시간·모델·토큰·유료 비용은 실제 자료·출처만 사용하고 미지원은 미확인으로 남기며 추정을 확정하거나 중복 합산하지 않아요. 사용자 예산 상한은 지키고 없으면 새 금액 상한·자동 차단·승인 요구를 만들지 않아요. 사용자 선택 모델·PM의 지원된 최고 추론과 전문가 강도에 대한 PM 판단을 유지해요. 관여한 역할은 정체/낭비 근거 → 중단·재사용·변경할 일 → 바로 할 다음 행동으로 짧게 반환하고 PM이 반영하거나 기존 진행·인계 기록에 구체적 예외 이유를 남겨요. 새 cron·승인자·대시보드·폴링 없이 반복 문서·전체 suite·불필요한 제한·승인·대기·확대를 줄여요. 원 요구·분모·필수 수용 조건·실제 사람 시험을 삭제하거나 미완료 개발을 사람에게 넘겨 완료율을 올리지 않고 확보한 유효 근거는 즉시 수용해요. 요구 ID·현재 버전·허용/제외 범위·질문·파일별 단일 작성자를 전달하고 편집 종료·진행 명령·branch/HEAD/remote ref·dirty·배포 버전·원격 검수 분모·unknown 대조·잔여/다음 담당을 확인해 인계해요. 실제 새 실행 연결이 없으면 nextExecutionRef는 null로 남기며 외부 사람/메일/Teams 발송은 별도 허용 범위를 확인해요.
동적 참조: pmThreadRef, currentTask, handoffRef, latestInstruction, goal, authorizedScope, priorCompleted, excludedScope, nextTask, nextExecutionRef. 실제 대화 ID·과거 별도 지시를 제품 가이드에 고정하지 않아요.
